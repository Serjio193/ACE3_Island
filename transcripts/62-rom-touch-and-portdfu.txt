# Video 62 — External ROM, touch behavior, PortDFU, and restore

Cleaned technical transcript. Greetings, soldering dead time, camera/OBS commentary, repetition, and unrelated backup discussion removed.

## 0:32–3:07 — Touch depends on the A3 path

After A3-related failures, technicians observed loss of:
- touch,
- charging,
- USB communication.

The schematic contains an **IO ACE-to-touch AID** signal. The author does not claim to know its exact internal meaning, but uses it as evidence that touch behavior depends on the USB controller path.

He notes similar historical coupling between touch and earlier Lightning USB-control ICs.

## 3:39–5:46 — What the external ROM does

The A3 is described as an ARM Cortex-M0-class microcontroller.

The chip contains internal boot code, but the external ROM/flash (shown as U9720 in the iPhone example) contains the **application code** needed for full operation.

Model used in the experiment:

```
A3 internal boot code
        ↓
external SPI ROM
        ↓
application firmware
        ↓
normal USB-C / PD / related operation
```

If the external application code is absent, unreadable, or rejected by the A3, the controller cannot fully boot.

## 8:04–11:15 — Normal/recovery/DFU observations

In normal and recovery operation the phone exposes normal device information.

When the device is placed into what the host tools call DFU, the USB layer appears as **Port DFU**. The host exposes an ECID-like identifier from this path.

The author distinguishes this PortDFU presentation from normal CPU/device identity.

## 12:55–17:18 — Blank the A3 ROM

The original external ROM is backed up with a CH341A SPI programmer and then erased.

After reinstalling the blank ROM:
- the phone itself can still power/boot far enough to show activity,
- the host sees a PortDFU/DFU device,
- normal A3 functions are absent because the A3 application firmware is missing.

## 22:00–28:30 — Original vs aftermarket display

With the ROM blank:

**Original Apple display**
- touch does not work.

**Tested aftermarket soft-OLED display**
- touch works.

The author concludes that the tested aftermarket screen does not require the same A3-to-touch AID condition that the original screen requires.

This is an observation for the tested display, not proof that all aftermarket screens behave the same way.

## 29:21–32:49 — Restore rebuilds a blank A3 ROM

Before restore:
- PortDFU is detected,
- normal USB communication is unavailable,
- charging is unavailable,
- original-screen touch is unavailable.

A restore is then performed.

After restore:
- USB communication returns,
- the A3 boots normally,
- charging/touch functionality returns.

The author concludes that the restore process **programmed usable A3 application firmware into the previously blank external ROM**.

## 32:56–35:52 — Data-preservation implication

Finder/iTunes DFU restore erases user data.

The author notes that 3uTools offers a “retain user data” style flash path and reports that it can restore A3 firmware while attempting to preserve data.

Separately, an aftermarket display may allow touch recovery even while the A3 ROM is mismatched/blank, which can provide another path to user-data access through the running OS/Wi-Fi.

## 36:11–40:47 — ROM before vs after Apple restore

The external ROM is dumped again after restore.

The author compares the original pre-test ROM dump with the post-restore dump using MD5 and finds they are **different**.

Observed conclusion:
- Apple restore reconstructed a working firmware image for the A3,
- but the resulting ROM image was not byte-identical to the original saved ROM.

## 41:27–42:20 — Practical conclusion

For the tested same-device situation, a missing/defective A3 external ROM does not necessarily require recovering the original ROM contents.

A blank/replacement ROM can be installed, after which restore can regenerate working A3 firmware.

The author presents:
- Finder/iTunes restore as the destructive path,
- 3uTools as a path that may preserve user data.

The key technical result is that **A3 application firmware can be regenerated by the restore process when the underlying A3/device pairing is otherwise acceptable**.
